# CarConnectivity migration

## What changed

On 2026-08-30 the bridge was migrated from unmaintained `weconnect-python` to:

- `carconnectivity` 0.11.10
- `carconnectivity-cli` 0.8.2
- `carconnectivity-connector-volkswagen` 0.10.6

The upstream core, CLI, and Volkswagen connector repositories were cloned. The
released packages were installed and tested in an isolated virtual environment
on the Raspberry Pi. The connector implements the writable resource
`/garage/<VIN>/commands/honk-flash`. Its accepted values are `flash` and
`honk-and-flash`; the bridge maps `/flash` and `/horn` to those values.

Credentials remain in the existing mode-protected `.env`. At command time the
bridge builds connector JSON in an anonymous Linux memory file and passes only
`/proc/self/fd/<fd>` to the child process. Token and cache files are stored in
the protected deployment directory so a future successful login can be reused.
Deployment removes the obsolete `weconnect` and `weconnect-cli` packages from a
reused virtual environment before installing the pinned successor packages.

## Live validation result

The read-only discovery command was run on the Pi with the real account. It
failed before credential submission:

```text
Authorization URL could not be fetched due to WeConnect failure
```

The connector requests
`https://emea.bff.cariad.digital/user-login/v1/authorize`; CARIAD responds with
HTTP 403 and no redirect. This is tracked in upstream
[issue 107](https://github.com/tillsteinbach/CarConnectivity-connector-volkswagen/issues/107).
Reports date the service-side change to 2026-05-27. Upstream `main` is the same
code as release 0.10.6 and contains no unreleased fix.

Current upstream analysis is that Volkswagen changed this public OAuth client
to require a private client assertion and Play Integrity/app attestation. That
proof is generated by the official mobile app and cannot be reproduced by a
Raspberry Pi client. Changing headers, adding PKCE, or replaying a captured
request does not satisfy the attestation requirement.

## Operational behavior

- `/healthz` remains `200` while Flask is alive.
- `/readyz` returns `503` with `vw_auth_unavailable` while authentication is
  blocked.
- `/flash` and `/horn` return sanitized errors without backend output.
- The off-device monitor continues alerting on degraded readiness.
- No honk command was sent during migration or validation.
- A live flash was not sent because writable-resource discovery could not
  authenticate.

## Recovery options

1. Upgrade the pinned Volkswagen connector after upstream restores a supported,
   command-capable authentication flow, then run `list --setters` and `/flash`.
2. Use the official Volkswagen app until then.
3. The EU Data Act connector can provide authorized read-only vehicle data, but
   the portal does not permit vehicle commands, so it cannot restore flash.
4. Production currently uses the official Android app fallback documented in
  [ANDROID_APP.md](ANDROID_APP.md). This preserves both SmartThings actions
  without attempting to bypass Volkswagen mobile attestation.

Do not implement mobile-attestation bypasses or copy official-app secrets into
this bridge. They expose the VW account and are not a production authentication
design.
